# 应用内 SSH 主机指纹确认

用户要求首次遇到未知 SSH 主机时在 Redix 中确认指纹，确认后写入程序自己的 known_hosts 并继续连接，不依赖系统 known_hosts。

## 方案与范围

采用握手时发现未知密钥、返回待确认凭据、用户确认后重新连接的方案。复用现有连接入口和确认对话框，避免另做预检连接；不持有等待用户操作的 SSH socket，以免占用连接超时预算和阻塞线程。当前分支实施，不创建分支、不自动提交或推送。

- 主机信任统一保存在 Tauri 应用数据目录的 `known_hosts`，不读取系统文件或旧连接中保存的自定义路径；旧路径字段仅为数据兼容保留，界面移除路径输入。
- 首次连接与测试连接显示 SSH 主机、端口、密钥算法和 `SHA256:` 指纹；默认聚焦取消，明确按钮为“信任并连接”。确认前取消、Escape、卸载均不保存、不重试；确认后离开页面不继续后续流程。
- 后端在认证前校验实际握手密钥。未知主机生成随机 UUID，后端内存保存 host/port/完整公钥，5 分钟过期，数量有界；前端只能提交 UUID，不能指定要信任的公钥或路径。
- 确认时在独立文件锁内重读、检查冲突、原子写入。仅未知或已经匹配的密钥允许保存；主机密钥变化一律拒绝，不能由首次信任弹框覆盖。
- 确认成功后重试原连接一次，每次连接及自动重连均重新校验。密钥在确认和重试之间变化也必须失败。持久化失败不得继续连接。
- 文件不存在视作空信任库；损坏、权限和其他读取失败要明确报错，不当作首次主机。

## 接口

`SSH_HOST_KEY_UNKNOWN` 错误含 `challenge_id`；其他错误码为 `SSH_HOST_KEY_CHANGED`、`SSH_HOST_KEY_STORE_FAILED`、`SSH_HOST_KEY_CHALLENGE_EXPIRED`。

- `get_ssh_host_key_challenge(challenge_id)` 返回 `{ challenge_id, host, port, algorithm, fingerprint }`。
- `trust_ssh_host_key(challenge_id)` 保存后端对应记录。
- `discard_ssh_host_key(challenge_id)` 丢弃未接受的记录。

密码、私钥、认证口令和本地文件路径不进入确认 DTO。保存连接本身不自动信任主机。

## 审查补充：迟到连接结果

打开连接成功返回该次发布的身份 token。若等待连接期间页面卸载或作用域变化，前端用 token 条件清理该次结果；后端核对当前已发布连接的身份再关闭。正在建立的新尝试单独跟踪，清理旧连接会让旧观察任务和缓存失效，但不能取消新尝试，也不能关闭后来发布的新连接。测试连接不发布活动句柄，不需要此清理。

## 手动清除信任记录

在编辑连接的 SSH 设置区域提供“SSH 主机信任”操作，用户确认后清除应用内全部已信任主机，无需保存设置。保留已有连接，后续新建 SSH 连接重新确认；不修改系统文件、连接配置或认证凭据。失败显示现有主机信任库错误。

后端 `clear_ssh_known_hosts()` 只操作应用固定信任库，使用与 trust 相同的独立文件锁和原子写。清除后文件只保留随机重置标记注释，所有清除前生成的 challenge（包括其他 store 实例及正在等待文件锁的确认）都不能恢复旧信任；本实例 pending 同时清空。缺失/已空文件可重复清除，损坏内容也可由此重置，写失败不报告成功。
